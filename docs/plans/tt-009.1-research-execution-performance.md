# TT-009.1 研究执行稳定性与性能优化 Plan

## 状态

核心实现已完成，待人工对照验收。本 Plan 是 TT-009 的稳定性补丁，优先于 TT-010；不修改 AO 或 GPT Researcher 上游源码。

### 已完成的自动化验证

- Node：`npm run typecheck` 与 `npm test`（180 项）通过。
- Python：`pytest test -q`（112 项）通过。
- 尚待一次真实任务的人工对照：确认历史 300 秒 AO 超时场景不会留下重叠 GPTR worker，并观察 AO 生成的独立研究分支能否在既有预算内并行。

## 目标

消除 AO 超时后旧 GPTR 研究仍继续运行造成的重复研究，并在不牺牲研究质量和来源可追溯性的前提下，缩短工作流关键路径、限制跨步骤上下文膨胀，让前端持续、诚实地展示检索后模型分析与写作阶段。

## 现状证据

2026-07-31 任务 `deb6c75f-7c7d-4d9d-a37b-358ad3a1ad2a` 提供了可复现证据：

- 工作流是 `research_heilongjiang_data → analyze_economic_trends → compile_final_report` 的严格串行链；`AO_CONCURRENCY=2` 无法并行存在依赖的步骤。
- 第一轮标准研究耗时 233.851 秒，其中检索后规划约 99 秒、报告写作约 98 秒；第二轮耗时 361.390 秒，检索约 27 秒，规划约 90 秒，写作约 244 秒。Tavily 不是主要瓶颈。
- YAML 声明 `llm.timeout: 300000`、`retry: 2`，而平台 `GPTR_RESEARCH_TIMEOUT_MS` 默认 30 分钟。
- AO 的外层 `withTimeout()` 到时只拒绝等待，不会取消传入 Promise；第二轮约 300 秒时启动了 `research-3`，而 `research-2` 仍继续运行。两轮分别报告约 0.6775 和 0.6765 美元估算成本。
- 综合请求同时包含 AO 已渲染的上游全文和 Evidence Bundle；Python 又渲染专家报告、来源及最多 20,000 字符研究上下文，总预算可达 120,000 字符，存在重复注入。
- GPTR 在 `conduct_research()` 与 `write_report()` 的长模型调用期间只提供阶段边界事件；前端只能显示“仍在运行”，容易被误解为卡死。

## 第一性原理决策

1. **先保证单次执行唯一，再优化速度。** 同一 AO 步骤的前一次研究未终止并完成清理时，不得开始重试。
2. **超时必须由内向外递增。** `研究截止时间 < 进程清理完成时间 < AO 步骤超时 < 任务总超时`；不能让不会取消底层工作的 AO 外层计时器先触发。
3. **只并行语义独立的工作。** 并行度不是越高越好；实际并行受 AO、任务研究预算和 Python worker 三者共同限制。
4. **依赖必须代表数据依赖，而不是显示顺序。** 不自动删除无法证明安全的依赖；由编排契约和保守校验避免无意义链式 DAG。
5. **上下文只传一次。** 综合步骤以 Evidence Bundle 为权威上游材料，不再同时传 AO 渲染全文；确定性裁剪优先于新增一次模型摘要。
6. **只展示已知事实。** 长模型调用显示阶段、已用时和最后活动时间，不伪造完成百分比或 token 流。

## 深模块与接口

### 1. 研究调用生命周期

在现有 TypeScript GPTR HTTP seam 和 Python进程执行器后形成一个深模块，隐藏截止时间计算、取消、清理和终态竞争：

```ts
type ResearchDeadline = {
  requestTimeoutMs: number;
  outerTimeoutMs: number;
  cleanupGraceMs: number;
};

resolveResearchDeadline({
  configuredResearchTimeoutMs,
  aoAttemptTimeoutMs,
}): ResearchDeadline;
```

跨语言 `ResearchRequest` 增加内部字段：

```json
{
  "researchRunId": "research-2",
  "executionTimeoutMs": 1800000
}
```

规则：

- 工作流生成时把 AO 研究步骤超时设为 `GPTR_RESEARCH_TIMEOUT_MS + cleanupGraceMs`，不再保留 AO 默认的 300 秒。
- `GptrConnector` 必须读取 AO 当前 attempt 的 `config.timeout`，拒绝形成“内层 30 分钟、外层 5 分钟”的反向层级。
- Python 使用请求级截止时间包裹 `ProcessResearchExecutor.execute()`；超时时先取消协程，等待 `_stop_process()` 完成，再返回稳定的 `research_execution_timeout`。
- GPTR 返回超时后 AO 才可以按自身策略重试；旧 worker 已不在活动集合中。
- 任务取消仍通过 `AbortSignal` 中断 HTTP；Researcher 流生成器必须等待取消任务完成，禁止只调用 `task.cancel()` 后立即退出。
- 终态采用 first-terminal-wins：超时、取消、成功、失败只能提交一个；截止时间后的事件、Evidence Bundle 和成本不得进入任务快照。

不修改 `node_modules/agency-orchestrator`；通过其已有 `llm.timeout`、`LLMConfig.timeout` 和平台连接器 seam 解决。

### 2. 工作流拓扑策略

新增纯计算 `WorkflowTopologyAnalysis`：

```ts
analyzeWorkflowTopology(workflow): {
  criticalPathLength: number;
  maximumWidth: number;
  researchBranchCount: number;
  warnings: TopologyWarning[];
};
```

编排契约增加：

- 可独立检索的事实、技术、市场、政策等研究步骤应作为并列根节点；
- `depends_on` 只能表达确实需要读取上游产出的数据依赖；
- 禁止仅为规定专家先后顺序而形成链；
- 唯一综合步骤使用 `synthesis`，并 fan-in 到所有必要研究分支；
- 必须使用 `{{output}}` 的分析步骤保留依赖，不强行并行。

校验器只对可证明的问题触发一次重新编排，例如：综合步骤未引用依赖输出、依赖 ID 不存在、声明独立研究却形成 ordering-only 链。语义不明确时给出结构化 warning，不自动改写 YAML。

运行并行度为：

```text
min(AO_CONCURRENCY, GPTR_TASK_CONCURRENCY_BUDGET, GPTR_WORKER_CONCURRENCY)
```

保留现有默认上限，避免私有模型服务被无限并发压垮。工作流事件增加关键路径长度、最大宽度和有效并行上限，便于解释为何某任务仍是串行。

### 3. 上下文预算

深化现有 `evidence_capture.py`，让一个接口负责公平分配而非调用方自行截断：

```py
render_synthesis_context(
    task_template,
    bundles,
    budget=SynthesisContextBudget(...),
) -> RenderedSynthesisContext
```

实施规则：

- `think_tank_runtime` 保存未渲染的 `taskTemplate`；综合请求使用模板指令，依赖全文只通过 `upstreamEvidence` 进入一次。
- 每个 Evidence Bundle 默认保留专家报告和去重来源；原始 `researchContext` 仅在专家报告缺失时作为回退，不再与完整报告重复注入。
- 总预算在所有依赖分支间公平分配，不能让第一个长报告耗尽额度；每个分支至少保留标题、结论开头和来源列表。
- URL、来源标题和引用关系优先保留；裁剪发生在结构边界，不截断 Markdown URL。
- 记录 `originalCharacters`、`selectedCharacters`、`truncatedBundles`，但不把完整上下文写入公开事件。
- standard/deep 的真正依赖步骤暂不压缩其业务输入；先通过拓扑去掉伪依赖，避免改变合法的链式分析语义。

## 可观测性与前端行为

复用现有 `ResearchPhase` 和研究 run 卡片，不新增大量时间线节点：

- 公开阶段固定为准备、规划、检索、收集、分析证据、撰写报告、整理交付、完成。
- 在没有新 GPTR 内容事件的长调用期间，每 20 秒发送轻量 `research.heartbeat`，只包含 run ID、当前阶段、阶段开始时间、总耗时和最后真实活动时间。
- heartbeat 更新当前 run 卡片，不增加研究活动数量、不增加执行节点、不进入展开后的内容列表。
- 卡片明确显示“正在分析已收集的 19 个来源”或“正在根据证据撰写报告”，并持续更新阶段耗时。
- 超时清理和 AO 重试显示为同一专家节点的 attempt 状态，例如“首轮超时，已完成清理，开始第 2/3 次”，不得伪装成新的专家。
- 并行专家分别显示运行状态；任务摘要显示“2 位专家并行研究中”。
- SSE 连接异常与模型仍在计算必须使用不同文案。

## 契约与配置

- 继续使用 `GPTR_RESEARCH_TIMEOUT_MS` 作为一次专家研究的业务截止时间。
- 新增可选 `GPTR_CLEANUP_GRACE_MS`，默认 20,000，要求小于 AO 外层超时；它只用于生命周期协调，不是额外研究时间。
- `.env.example` 说明三个并发配置和两个超时配置之间的关系。
- `ResearchProgress` 增加可选 `attempt`、`maxAttempts`、`phaseStartedAt`、`lastActivityAt`；保持 schemaVersion 1 的向后兼容可选字段。
- 新公开事件使用稳定类型 `research.heartbeat`、`research.retrying`；不得包含提示词、密钥、原始异常或完整上下文。
- 历史任务、历史 YAML 和 Evidence Bundle 无需迁移。

## TDD 实施顺序

### 阶段 A：正确性——先消除重叠研究

1. Node 截止时间计算测试：短 AO timeout、30 分钟 GPTR timeout、`timeout: 0`、非法配置。
2. Python 进程取消测试：挂起引擎到期后 worker 被终止、活动集合清空、只返回一个稳定终态。
3. 流断开测试：客户端取消后生成器等待执行任务清理，worker 不残留。
4. GPTR connector 合约测试：传递 run ID 和研究截止时间；超时后的迟到事件、证据和成本被丢弃。
5. AO retry 集成测试：首次研究超时，确认旧 worker 清理完成后才开始第二次；峰值同 step 活动 worker 数为 1。
6. 工作流 compose 测试：生成的研究步骤外层 timeout 大于研究截止时间，当前约 6 分钟研究不会在 300 秒重复启动。

### 阶段 B：性能——缩短关键路径

7. 拓扑分析纯函数测试：串行链、fan-out/fan-in、合法链式分析、交互步骤和单步骤任务。
8. 编排契约与重编排测试：独立研究分支并列，最终 synthesis 正确引用全部输出；不删除真实依赖。
9. 有界并发测试：两个独立 standard 分支可以重叠运行，但不超过三个现有并发上限中的最小值。
10. 综合上下文测试：上游全文不重复、分支公平分配、来源链接不截断、缺失报告时使用 bounded context 回退。
11. 体积回归测试：多个长报告的最终请求保持在预算内，并输出可诊断的裁剪统计。

### 阶段 C：体验——真实阶段反馈

12. heartbeat 状态机测试：长分析/写作每 20 秒更新，阶段切换重置计时，终态后立即停止。
13. 事件投影测试：heartbeat 不增加 activityCount、sourceCount 或时间线节点；retry attempt 正确归并。
14. 前端测试：阶段中文、实时耗时、并行专家摘要、SSE 断线文案及展开研究事件保持兼容。
15. 全量执行 Node 测试、Pytest、typecheck、build、acceptance 和三平台文档导出回归。

## 范围与非目标

本项不修改 AO/GPTR 上游源码，不更换模型，不新增检索器或抓取器，不实现分布式队列，不引入 Redis/Celery，不自动摘要每个专家报告，不承诺所有任务都可并行，也不展示虚构的百分比。模型自身吞吐、私有推理服务排队和 GPTR 内部不可见的 token 生成仍可能影响耗时，但平台必须准确显示当前阶段且不得制造重复调用。

## 验收标准

- 任一 AO step 的旧 GPTR worker 完成清理前不会启动该 step 的重试；测试期间同 step 峰值活动 worker 数恒为 1。
- 研究超过 300 秒但未超过 `GPTR_RESEARCH_TIMEOUT_MS` 时只产生一个 Research Bundle 和一次成本记录。
- 用户取消、研究超时、任务超时均无残留 Python worker，且只有一个终态。
- 独立研究 fixture 形成 fan-out/fan-in 并真实并行；合法数据依赖仍保持串行。
- 综合请求不再同时携带 AO 渲染全文和同一 Evidence Bundle；上下文预算公平且所有保留事实仍可追溯到 URL。
- 规划、分析或写作超过 20 秒时，前端持续更新阶段与耗时；heartbeat 不污染事件计数。
- 当前单 DuckDuckGo/Tavily、多检索器、URL-only、URL+Web、standard/deep/synthesis 和导出行为无回归。
- Node、Python、typecheck、build、acceptance 全部通过，并用“黑龙江近三年经济发展”同类任务完成一次人工对照验收。

## 人工基准

实施前保存同一话题、相同 Profile、相同模型和检索器的：

- AO 编排耗时；
- 每个 run 的检索、分析、写作、验收耗时；
- 调用次数、重试次数、唯一来源数、输入上下文字符数和估算成本；
- 工作流关键路径、最大并行宽度及总墙钟时间。

实施后至少运行三次，比较中位数。正确性门槛是零重叠重复研究；性能目标是独立多专家任务总墙钟时间明显低于等价串行关键路径，来源数和验收结果不得因优化显著下降。

## 回滚

三个阶段可独立回滚：

1. 生命周期异常时关闭请求级截止时间字段，保留已提高的 AO timeout，避免恢复 300 秒重叠重试。
2. 拓扑策略异常时关闭 topology recompose，仅保留分析 warning，工作流恢复 AO 原始依赖。
3. 上下文预算异常时恢复旧 synthesis renderer；heartbeat 可独立关闭，不影响研究执行。

任何回滚都不能恢复“AO 外层 timeout 先于 GPTR 清理”的旧配置。
